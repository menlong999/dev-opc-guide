## 按依赖安排发布顺序

我这套产品先发布 CLI 包，再核对连接器安装的精确版本；专家单独准备依赖和包内容；Buddy App 再配置所需专家、模式、场景和引导入口。每层都查看自己的提交与发布结果。

这是一条具体产品的依赖路线。先确定你需要什么资产，再安排顺序，不要求所有开发者都额外做齐三种形态。

## 连接器、专家和 Buddy App，分别解决什么问题？

在我的 DxC 接入中，连接器提供 CLI（命令行工具）及相关能力；专家组织工作方式并声明依赖；Buddy App 提供面向用户的模式、场景和入口。

它们是不同资产。一个通过，不能推定另外两个也已发布。先画清自己真正需要哪几层，以及每层依赖什么。

<a id="q059"></a>

## 连接器在本地能跑，为什么 Windows 审核机找不到 npm？

我的驳回最初是乱码，恢复后是“npm 不是内部或外部命令”。当时失败在安装阶段，业务登录与付款代码还没运行。

复审采用 Node.js 22 配置基线，CLI 最低要求仍是 22.16.0，并固定包版本和来源；0.1.2 后来通过。这不能证明审核机一定没装 Node，运行时准备和命令路径都要检查。

<a id="q060"></a>

## Git 仓库、npm 包、连接器和技能版本，怎么对应？

分别记录源码提交、CLI 包版本、连接器版本与技能版本。我的仓库改动曾经和同号 npm 包内容不同，市场用户并不会自动装到本地最新代码。

发布后从用户实际安装入口重新装一次，确认功能和同版技能都在，再更新依赖它的资产。

<a id="q061"></a>

## 没有用开放接口，Buddy App 为什么还卡在授权列表？

我当时空选无法保存，最后只申请了基础昵称与头像。填写时要逐项说明业务用途，核对哪些权限实际会被使用。

如果表单和实际需要不一致，先确认必填条件或联系平台，不要为了过表单随便勾高级权限。

<a id="q062"></a>

## 市场展示分类和服务类目，为什么要分别确认？

我发现这两项不是同一个字段，最终为写作工具选择了匹配实际服务的“工具 → 办公”。其他类目可能带出不同资质字段。

按真实业务选类目，先读字段说明。不能把我这次的选择写成所有产品都用同一类目绕过资质要求。

<a id="q063"></a>

## 创建获批之后，为什么还要配置专家、再等配置审核？

Buddy App 基础申请通过后，我又经历了配置审核。反馈明确要求至少配置一个专家，于是继续做依赖现有连接器的专家包。

将“创建通过”“配置提交”“配置审核”和“发布”分开记录，核对实际反馈。不要拿创建成功截图当作整个应用已经公开。

<a id="q064"></a>

## 浅色模式正常，深色图标和引导入口为什么还会返工？

图标曾被要求与旁边文字同色。我检查了 3 个模式、15 个场景的 18 处引用，并在客户端看浅色、深色和选中状态。

另一个问题是填了 15 条引导，客户端只显示前 3 条；后来改成三个主要入口，完整教程放到网站。这里是引导条目，不是“15 个场景只剩 3 个”。

<a id="q065"></a>

## 专家已经声明连接器依赖，为什么还报缺少 14 项技能？

第一版 Agent（智能体）文件声明了预加载并引用技能，但包内没有对应资源。连接器依赖、包内技能和预加载字段，被我混在了一起。

后来删预加载、调整文字和表格，仍经历缺 3 项的反馈。重新核对完整文本、依赖和打包内容再提交，不能只看本地检查通过。

<a id="q066"></a>

## 专家名称被占用、提交次数有限，怎么减少无效重提？

区分展示名与包内唯一标识。我换新资产时，旧标识仍被占用，后来同步调整 `name` 和插件标识才继续。

当时我记录过每日提交三次的限制，所以要求先看完整文字再打包。现在应查看自己后台的实际额度；不要把当时观察写成平台永久规则，也不要猜一次就提交一次。

<a id="q067"></a>

## Skill 上架、开通付费、用户买完能安装，是同一件事吗？

分开确认三条链：内容或工具能否上架，卖方是否能开通收款，买方付款后能否拿到并安装正确版本。安装成功也不等于后续更新与退款已经有安排。

先向目标平台确认是否支持你的售卖方式、结算和退款机制，再准备商品说明、依赖、兼容宿主和交付范围。WorkBuddy 资产获批不能直接推定已拥有付费 Skill 售卖能力。
